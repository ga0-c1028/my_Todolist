## 1. 개요 및 목적

본 문서는 인증 기반 개인 할일 관리 웹앱 "my_Todolist"의 사용자 시나리오를 정의한다. `docs/1-domain_definition.md`의 용어·엔티티·상태 규칙·비즈니스 규칙(BR)과 `docs/2-prd.md`의 기능 요구사항(FR-01~FR-13)을 근거로, 실제 사용 흐름을 사용자 행동과 시스템 반응 단위로 구체화하는 것을 목적으로 한다. 각 시나리오에는 관련 FR ID와 BR ID를 함께 표기하여 요구사항 추적성을 유지한다.

## 2. 대상 사용자

PRD 3장에 정의된 바와 같이 학생 및 20대~50대 직장인으로, 개인 일정과 과제·업무를 스스로 관리하려는 사용자를 대상으로 한다. 상세 페르소나는 PRD에서 생략하기로 하였으므로, 본 문서에서도 시나리오별로 필요한 최소한의 역할만 명시한다(예: "대학생 사용자", "직장인 사용자").

## 3. 시나리오 문서 표기 규칙

각 시나리오는 다음 항목으로 구성한다.

- **목적**: 시나리오가 검증하고자 하는 사용 흐름 또는 규칙
- **관련 FR/BR**: 근거가 되는 기능 요구사항 ID와 비즈니스 규칙 ID
- **사전 조건**: 시나리오 시작 전 갖춰야 할 상태
- **단계별 흐름**: 사용자 행동 → 시스템 반응 순서로 서술
- **기대 결과(성공 기준)**: 시나리오 완료 시 충족되어야 하는 조건

## 5. End-to-End 시나리오

### SC-01. 회원가입부터 할일 완료·로그아웃까지의 전체 흐름

- **목적**: 신규 사용자가 회원가입부터 할일 등록·조회·수정·완료 처리·로그아웃까지 서비스의 핵심 기능을 순서대로 사용할 수 있음을 검증한다.
- **관련 FR/BR**: FR-01, FR-02, FR-05, FR-07, FR-08, FR-09, FR-10, FR-12, FR-03 / BR-1, BR-3, BR-6, BR-8
- **사전 조건**: 대학생 사용자가 my_Todolist를 처음 사용하며, 계정이 존재하지 않는다.
- **단계별 흐름**:
  1. 사용자가 회원가입 화면에서 이메일, 비밀번호(영문·숫자 포함 8자 이상), 이름을 입력하고 제출한다. → 시스템은 이메일 중복 여부와 형식·길이 제약을 검증한 뒤 계정을 생성하고, 사용자별 '기본' 카테고리를 자동으로 생성한다.(FR-01)
  2. 사용자가 로그인 화면에서 동일한 이메일과 비밀번호로 로그인한다. → 시스템은 인증에 성공하면 access_token과 refresh_token을 발급하고, 이후 요청에는 access_token을 사용하도록 안내한다.(FR-02)
  3. 사용자가 카테고리 관리 화면에서 "학교 과제"라는 이름의 카테고리를 생성한다. → 시스템은 사용자 내 이름 중복이 없음을 확인하고 카테고리를 생성한다.(FR-05)
  4. 사용자가 할일 등록 화면에서 제목 "데이터베이스 과제 제출", 카테고리 "학교 과제", 캘린더 UI로 시작일자와 종료일자(시작일자 이상)를 지정하고 등록한다. → 시스템은 종료일자가 시작일자 이상인지 검증한 뒤(BR-6) 할일을 생성한다.(FR-07)
  5. 사용자가 할일 목록 화면에서 "학교 과제" 카테고리로 필터링하여 방금 등록한 할일을 확인한다. → 시스템은 조회 시점의 시작일자·종료일자·완료 여부를 기준으로 상태(시작 전/진행중/완료/기한초과)를 계산해 함께 표시한다.(FR-08, FR-09)
  6. 사용자가 해당 할일의 편집 화면에서 제목을 "데이터베이스 과제 제출(최종본)"로 수정하고 저장한다. → 시스템은 소유자 본인임을 확인한 뒤 변경 사항을 저장한다.(FR-10)
  7. 사용자가 과제를 마친 후 할일을 완료로 처리한다. → 시스템은 `isCompleted`를 true로 변경하고 `completedAt`을 현재 일시로 기록하며, 목록에서 상태를 '완료'로 표시한다.(FR-12)
  8. 사용자가 로그아웃을 요청한다. → 시스템은 refresh_token을 무효화하고 세션을 종료한다.(FR-03)
- **기대 결과(성공 기준)**: 회원가입, 로그인, 카테고리 생성, 할일 등록·조회·필터링·수정·완료 처리, 로그아웃이 오류 없이 순차적으로 완료되고, 각 단계의 결과가 다음 단계에서 정상적으로 반영된다.

## 6. 보조 시나리오(핵심 기능)

### SC-02. 카테고리 삭제 시 소속 할일의 기본 카테고리 자동 이관

- **목적**: '기본'이 아닌 카테고리를 삭제할 때 소속 할일이 유실되지 않고 '기본' 카테고리로 자동 이관됨을 검증한다.
- **관련 FR/BR**: FR-06 / BR-4, BR-5
- **사전 조건**: 직장인 사용자가 로그인 상태이며, "업무" 카테고리에 할일 2건이 등록되어 있다.
- **단계별 흐름**:
  1. 사용자가 카테고리 관리 화면에서 "업무" 카테고리 삭제를 요청한다. → 시스템은 해당 카테고리가 '기본' 카테고리가 아님을 확인하고 삭제를 진행한다.(BR-4)
  2. 시스템은 "업무" 카테고리에 속해 있던 할일 2건의 `categoryId`를 해당 사용자의 '기본' 카테고리로 일괄 변경한다.(BR-5)
  3. 사용자가 할일 목록을 조회한다. → 시스템은 삭제된 카테고리 없이, 기존 2건의 할일을 '기본' 카테고리 소속으로 정상 표시한다.
- **기대 결과(성공 기준)**: "업무" 카테고리는 목록에서 사라지고, 소속 할일 2건은 삭제되지 않은 채 '기본' 카테고리로 조회된다.

### SC-03. 상태 기준 할일 목록 필터링(기한초과 포함)

- **목적**: 할일 목록을 상태(시작 전/진행중/완료/기한초과) 기준으로 필터링할 수 있으며, 완료된 할일은 종료일자 경과 여부와 무관하게 '기한초과'로 분류되지 않음을 검증한다.
- **관련 FR/BR**: FR-08, FR-09 / BR-7, BR-8, 도메인 정의서 5장 상태 판단 규칙
- **사전 조건**: 사용자가 로그인 상태이며, 다음과 같은 할일이 등록되어 있다.
  - 할일 A: 종료일자가 오늘 이전이며 미완료(`isCompleted = false`)
  - 할일 B: 종료일자가 오늘 이전이나 완료 처리됨(`isCompleted = true`)
  - 할일 C: 시작일자가 오늘 이후이며 미완료
- **단계별 흐름**:
  1. 사용자가 할일 목록 화면에서 '기한초과' 필터를 선택한다. → 시스템은 `isCompleted = false`이고 `endDate < today`인 할일만 조회하여 할일 A를 반환한다.(BR-7)
  2. 사용자가 '완료' 필터로 전환한다. → 시스템은 `isCompleted = true`인 할일 B를 반환한다.
  3. 사용자가 '시작 전' 필터로 전환한다. → 시스템은 `isCompleted = false`이고 `today < startDate`인 할일 C를 반환한다.
- **기대 결과(성공 기준)**: 완료 처리된 할일 B는 종료일자가 지났음에도 '기한초과' 필터 결과에 포함되지 않고 '완료' 필터 결과에만 나타나며, 나머지 필터 결과도 상태 판단 규칙과 일치한다.

### SC-04. access_token 만료 후 refresh_token을 통한 무중단 재인증

- **목적**: access_token이 만료되었을 때 사용자가 재로그인 없이 refresh_token으로 access_token을 재발급받아 서비스 이용을 이어갈 수 있음을 검증한다.
- **관련 FR/BR**: FR-13 / BR-1
- **사전 조건**: 사용자가 로그인하여 access_token과 refresh_token을 보유하고 있으며, access_token의 유효 시간이 경과하여 만료되었다.
- **단계별 흐름**:
  1. 사용자가 할일 목록 조회를 요청한다. → 시스템은 access_token이 만료되었음을 확인하고 401 Unauthorized로 응답한다.(BR-1)
  2. 클라이언트는 보유한 refresh_token으로 토큰 재발급을 요청한다. → 시스템은 refresh_token의 유효성을 검증하고 새로운 access_token을 발급한다.(FR-13)
  3. 클라이언트는 재발급받은 access_token으로 이전에 실패했던 할일 목록 조회를 재요청한다. → 시스템은 정상적으로 목록을 반환한다.
- **기대 결과(성공 기준)**: 사용자는 로그인 화면으로 이동하거나 자격 증명을 다시 입력하지 않고도 요청이 최종적으로 성공하며, 서비스 이용이 중단 없이 이어진다. 단, refresh_token마저 만료·무효화된 경우에는 재로그인이 요구된다.

### SC-05. 할일 완료 처리 및 완료 취소

- **목적**: 할일을 완료 처리하거나 완료를 취소했을 때 `completedAt` 값과 상태 표시가 규칙에 따라 갱신됨을 검증한다.
- **관련 FR/BR**: FR-12 / BR-2, 도메인 정의서 3.3절 completedAt 규칙
- **사전 조건**: 사용자가 소유한 할일이 '진행중' 상태로 존재한다.
- **단계별 흐름**:
  1. 사용자가 할일을 완료로 표시한다. → 시스템은 `isCompleted`를 true로, `completedAt`을 현재 일시로 설정하고 상태를 '완료'로 표시한다.
  2. 사용자가 같은 할일의 완료를 취소한다. → 시스템은 `isCompleted`를 false로 되돌리고 `completedAt`을 null로 초기화하며, 시작일자·종료일자를 기준으로 상태를 재계산해 표시한다.
- **기대 결과(성공 기준)**: 완료·취소 조작에 따라 `completedAt`이 규칙대로 설정·초기화되고, 화면에 표시되는 상태가 매 시점 최신 규칙을 반영한다.

## 7. 보조 시나리오(확장 기능)

### SC-06. 회원 정보(이름·비밀번호) 수정

- **목적**: 로그인한 사용자가 본인의 이름과 비밀번호만 수정할 수 있고 이메일은 수정 대상에서 제외됨을 검증한다.
- **관련 FR/BR**: FR-04 / BR-9, BR-10
- **사전 조건**: 사용자가 로그인 상태이다.
- **단계별 흐름**:
  1. 사용자가 회원 정보 수정 화면에 진입한다. → 시스템은 이메일 필드를 수정 불가 상태로 표시한다.(BR-9)
  2. 사용자가 이름과 새 비밀번호를 입력하고 저장한다. → 시스템은 이름·비밀번호 제약(이름 1~30자, 비밀번호 8자 이상 영문·숫자 포함)을 검증한 뒤 저장하고 `updatedAt`을 갱신한다.(BR-10)
- **기대 결과(성공 기준)**: 이름과 비밀번호는 정상적으로 변경되며, 이메일은 변경되지 않은 채 유지된다.

### SC-07. 카테고리 이름 수정

- **목적**: '기본'이 아닌 카테고리의 이름은 수정할 수 있으나, '기본' 카테고리는 이름 수정이 불가함을 검증한다.
- **관련 FR/BR**: FR-06 / BR-4
- **사전 조건**: 사용자가 '기본' 카테고리와 "취미"라는 이름의 카테고리를 각각 보유하고 있다.
- **단계별 흐름**:
  1. 사용자가 "취미" 카테고리의 이름을 "운동"으로 수정 요청한다. → 시스템은 사용자 내 이름 중복이 없음을 확인하고 이름을 변경한다.
  2. 사용자가 '기본' 카테고리의 이름 수정을 시도한다. → 시스템은 '기본' 카테고리는 이름 수정이 불가함을 안내하고 요청을 거부한다.(BR-4)
- **기대 결과(성공 기준)**: 일반 카테고리는 이름이 정상 변경되고, '기본' 카테고리는 이름이 변경되지 않는다.

### SC-12. 회원 탈퇴

- **목적**: 로그인한 사용자가 확인 절차를 거쳐 본인 계정을 영구히 삭제할 수 있고, 삭제 시 소유 데이터도 함께 정리됨을 검증한다.
- **관련 FR/BR**: FR-14 / BR-12
- **사전 조건**: 사용자가 로그인 상태이며, 본인 소유의 카테고리와 할일을 보유하고 있다.
- **단계별 흐름**:
  1. 사용자가 회원 정보 수정 화면에서 "회원 탈퇴"를 클릭한다. → 시스템은 "탈퇴 시 계정과 모든 카테고리·할일이 영구히 삭제되며 되돌릴 수 없습니다"라는 확인 대화상자를 노출한다.
  2. 사용자가 확인을 클릭한다. → 시스템은 계정과 소유 카테고리·할일·refresh_token을 삭제하고 로그인 화면으로 이동한다.(BR-12)
  3. 사용자가 탈퇴한 계정으로 다시 로그인을 시도한다. → 시스템은 인증 실패로 응답한다.
- **기대 결과(성공 기준)**: 확인 전에는 계정이 삭제되지 않으며, 확인 후에는 계정과 소유 데이터가 모두 삭제되어 동일 자격 증명으로 재로그인할 수 없다.

### SC-13. 라이트/다크 모드 전환

- **목적**: 헤더의 토글로 화면 테마를 전환할 수 있고, 선택한 테마가 재방문 시에도 유지됨을 검증한다.
- **관련 FR/BR**: FR-15 / -
- **사전 조건**: 사용자가 로그인 상태이며, 현재 라이트 모드로 화면이 표시되어 있다.
- **단계별 흐름**:
  1. 사용자가 헤더의 테마 토글 버튼을 클릭한다. → 시스템은 배경·카드·텍스트·테두리 색상을 다크 팔레트로 즉시 전환하고, 선택값을 브라우저(localStorage)에 저장한다.
  2. 사용자가 페이지를 새로고침한다. → 시스템은 저장된 다크 모드 설정을 유지한 채로 화면을 표시한다.
- **기대 결과(성공 기준)**: 토글 클릭 시 테마가 즉시 전환되고, 새로고침 후에도 마지막으로 선택한 테마가 유지된다.

### SC-14. 언어 전환

- **목적**: 헤더의 언어 선택으로 화면의 정적 UI 문구가 한국어/영어/일본어로 전환되고, 사용자가 입력한 데이터(카테고리명 등)는 번역되지 않음을 검증한다.
- **관련 FR/BR**: FR-16 / -
- **사전 조건**: 사용자가 로그인 상태이며, "업무"라는 이름의 카테고리를 보유하고 있다.
- **단계별 흐름**:
  1. 사용자가 헤더의 언어 선택에서 "English"를 선택한다. → 시스템은 내비게이션, 버튼, 폼 라벨 등 정적 UI 문구를 영어로 전환하고, 선택값을 브라우저(localStorage)에 저장한다.
  2. 사용자가 할일 목록 화면을 확인한다. → 시스템은 "업무" 카테고리명은 원문 그대로 표시한다.
- **기대 결과(성공 기준)**: 정적 UI 문구만 선택한 언어로 전환되고, 사용자가 입력한 데이터는 언어 전환과 무관하게 원문이 유지된다.

## 8. 예외 시나리오

### SC-08. 중복 이메일로 회원가입 시도

- **목적**: 이미 가입된 이메일로 재가입을 시도할 경우 계정이 생성되지 않고 적절한 오류가 반환됨을 검증한다.
- **관련 FR/BR**: FR-01 / BR-9
- **사전 조건**: `user@example.com`으로 가입된 계정이 이미 존재한다.
- **단계별 흐름**:
  1. 신규 사용자가 동일한 이메일 `user@example.com`으로 회원가입을 시도한다. → 시스템은 이메일 중복을 확인하고 계정을 생성하지 않은 채 오류를 반환한다.(BR-9)
- **기대 결과(성공 기준)**: 계정이 추가로 생성되지 않으며, 사용자는 이메일이 이미 사용 중임을 인지할 수 있는 오류 메시지를 확인한다.

### SC-09. 타인 소유 할일에 대한 접근 시도

- **목적**: 인증된 사용자라도 본인이 소유하지 않은 할일에는 조회·수정·삭제할 수 없음을 검증한다.
- **관련 FR/BR**: FR-10, FR-11 / BR-2
- **사전 조건**: 사용자 A와 사용자 B가 각각 로그인 가능한 계정을 보유하고 있으며, 할일은 사용자 A 소유이다.
- **단계별 흐름**:
  1. 사용자 B가 로그인 후, 사용자 A 소유의 할일 ID를 이용해 수정 또는 삭제를 요청한다. → 시스템은 요청자와 할일의 소유자가 일치하지 않음을 확인하고 403 Forbidden으로 응답한다.(BR-2)
- **기대 결과(성공 기준)**: 사용자 A의 할일은 변경·삭제되지 않고 그대로 유지되며, 사용자 B는 접근 권한이 없다는 응답을 받는다.

### SC-10. 종료일자가 시작일자보다 빠른 할일 등록 시도

- **목적**: 할일 등록·수정 시 종료일자가 시작일자보다 빠르면 저장이 거부됨을 검증한다.
- **관련 FR/BR**: FR-07, FR-10 / BR-6
- **사전 조건**: 사용자가 로그인 상태이며 할일 등록 화면에 접근해 있다.
- **단계별 흐름**:
  1. 사용자가 캘린더 UI에서 시작일자를 2026-09-10, 종료일자를 2026-09-05로 지정하고 등록을 시도한다. → 시스템은 종료일자가 시작일자보다 빠름을 확인하고 할일을 생성하지 않은 채 오류를 반환한다.(BR-6)
- **기대 결과(성공 기준)**: 유효하지 않은 일자 조합의 할일이 생성되지 않으며, 사용자는 종료일자를 시작일자 이상으로 다시 지정하도록 안내받는다.

### SC-11. 로그인 실패 시 동일한 오류 메시지 응답

- **목적**: 이메일 미존재와 비밀번호 불일치라는 서로 다른 원인의 로그인 실패가 동일한 오류 메시지로 응답되어 계정 존재 여부가 노출되지 않음을 검증한다.
- **관련 FR/BR**: FR-02 / BR-11
- **사전 조건**: `existing@example.com`은 가입된 이메일이고, `unknown@example.com`은 가입되지 않은 이메일이다.
- **단계별 흐름**:
  1. 사용자가 `unknown@example.com`과 임의의 비밀번호로 로그인을 시도한다. → 시스템은 이메일이 존재하지 않음을 원인으로 노출하지 않고 공통 오류 메시지를 반환한다.
  2. 사용자가 `existing@example.com`과 잘못된 비밀번호로 로그인을 시도한다. → 시스템은 비밀번호 불일치를 원인으로 노출하지 않고 동일한 공통 오류 메시지를 반환한다.(BR-11)
- **기대 결과(성공 기준)**: 두 실패 케이스 모두 동일한 오류 메시지가 반환되어, 응답만으로는 해당 이메일의 가입 여부를 구분할 수 없다.
