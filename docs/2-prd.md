## 1. 문서 개요

### 1.1 목적
본 문서는 인증 기반 개인 할일 관리 웹앱 "my_Todolist"의 제품 요구사항을 정의한다. `docs/1-domain_definition.md`에서 정의한 도메인 지식(용어, 엔티티, 상태 규칙, 비즈니스 규칙, 유스케이스)을 근거로 실제 개발에 착수할 수 있는 수준의 기능·비기능 요구사항, 기술 제약, 일정을 구체화하는 것을 목적으로 한다.

### 1.2 배경
사용자가 인증된 개인 단위로 할일을 관리하고, 시작일·종료일을 함께 다룰 수 있는 앱이 부재하다(도메인 정의서 REQ-01, REQ-02). 이를 해결하기 위해 카테고리 분류, 캘린더 기반 일정 지정, 상태별 필터링 기능을 갖춘 웹 애플리케이션을 개발한다.

## 2. 제품 목표 및 성공 지표

### 2.1 제품 목표
- 인증된 사용자가 본인의 할일을 카테고리별로 등록·관리할 수 있다.
- 할일의 시작일·종료일을 캘린더 UI로 지정하고, 상태(시작 전/진행중/완료/기한초과)를 자동으로 파악할 수 있다.
- 데스크톱과 모바일 브라우저 모두에서 반응형 웹 UI로 동일한 기능을 사용할 수 있다.

### 2.2 성공 지표(KPI)
| 지표 | 목표치 | 비고 |
|---|---|---|
| 동시 접속 처리량 | 1,000명 동시 접속 시 서비스 정상 동작 | 비즈니스 목표. 2.5절 성능 기준과 연계 |
| 핵심 기능 완성도 | MVP 범위(4.1절) 100% 구현 | 2일 개발 일정 내 |
| 반응형 UI 적용률 | 전체 화면 100% | 모바일·데스크톱 뷰포트 모두 대응 |

## 3. 대상 사용자

- 학생 및 20대~50대 직장인. 개인 일정과 과제·업무를 스스로 관리하려는 사용자를 대상으로 한다.
- 상세 페르소나(연령별 세부 시나리오 등)는 본 문서 범위에서 생략한다.

## 4. 범위

### 4.1 In Scope
- 회원가입, 로그인, 로그아웃 (REQ-F01)
- 회원 정보(이름, 비밀번호) 수정 (REQ-F03)
- 카테고리 등록·수정·삭제, 미지정 시 '기본' 카테고리 자동 적용 (REQ-F02)
- 할일 등록·수정·삭제·완료 처리, 캘린더 UI를 통한 시작일·종료일 지정 (REQ-F04, REQ-F06, REQ-F07)
- 할일 목록의 카테고리별·상태별(시작 전/진행중/완료/기한초과) 필터링 (REQ-F05)
- 데스크톱·모바일 브라우저 대응 반응형 웹 UI

### 4.2 Out of Scope
- 네이티브 모바일 앱(iOS/Android) 개발. 모바일은 반응형 웹 UI로만 대응한다.
- 웹 접근성(WCAG 등) 대응. 본 프로젝트에서는 접근성 요구사항을 고려하지 않는다.
- 사용자 간 협업 기능(할일 공유, 담당자 지정 등), 알림/리마인더, 통계·리포트 기능.
- 소셜 로그인, 비밀번호 찾기/재설정, 이메일 인증.
- 오프라인 지원, 다국어(i18n) 지원.

## 6. 비기능 요구사항

| ID | 구분 | 요구사항 |
|---|---|---|
| NFR-01 | 성능/동시접속 | 서비스는 1,000명 동시 접속 상황에서 정상적으로 응답해야 한다(비즈니스 목표). 구체적인 응답 시간·처리량 기준은 부하 테스트를 통해 별도 검증한다. |
| NFR-02 | 반응형 UI | 모든 화면은 데스크톱과 모바일 브라우저 뷰포트에서 레이아웃이 정상적으로 동작하는 반응형 웹 UI로 구현한다. |
| NFR-03 | 보안 | 비밀번호는 해시로 저장하며, 인증되지 않은 요청은 401, 타인 소유 데이터 접근 시 403으로 응답한다(도메인 정의서 BR-1, BR-2 준수). 인증은 JWT 기반으로 하며 access_token(단기 유효)과 refresh_token(장기 유효)을 함께 발급한다. |
| NFR-04 | 데이터 정합성 | 할일의 종료일자는 시작일자 이상이어야 하며(BR-6), 카테고리 삭제 시 소속 할일 유실이 없어야 한다(BR-5). |
| NFR-05 | 접근성 | 본 프로젝트에서는 웹 접근성(WCAG 등)을 요구사항으로 다루지 않는다. |

## 7. 기술 스택 및 아키텍처 제약

### 7.1 프론트엔드
- React 19 + TypeScript
- 라우팅: React Router (`createBrowserRouter`, 인증 가드 포함)
- 전역 상태관리: Zustand
- 서버 상태 동기화: TanStack Query (백엔드 API와의 데이터 페칭·캐싱·동기화 담당)
- 반응형 웹 UI 필수 적용(별도 모바일 전용 코드베이스 없음)

### 7.2 백엔드
- Node.js + JavaScript + Express
- DB 접근은 `pg` 라이브러리를 사용한 원시 SQL 또는 직접 작성한 쿼리로 처리한다. Prisma 등 ORM은 사용하지 않는다.
- 이 제약에 따라 스키마 마이그레이션과 쿼리 작성을 수동으로 관리해야 하며, SQL 인젝션 방지를 위해 `pg`의 파라미터화 쿼리(prepared statement)를 반드시 사용한다.
- 인증 방식은 JWT를 사용하며, access_token과 refresh_token을 함께 발급한다. access_token은 API 요청 인증에 사용하는 단기 토큰이고, refresh_token은 access_token 재발급에만 사용하는 장기 토큰이다.

### 7.3 데이터베이스
- PostgreSQL 17
- 도메인 정의서 3장의 User, Category, Todo 엔티티를 테이블로 매핑하며, 소유자 기반 접근 제어(BR-2)를 쿼리 조건(WHERE user_id = ...)으로 구현한다.

### 7.4 아키텍처 함의
- ORM 미사용으로 인해 데이터 접근 계층의 반복 코드가 늘어날 수 있으므로, 공통 쿼리 헬퍼 함수 정도의 최소한의 구조화는 필요하다.
- 1,000명 동시접속 목표(NFR-01) 대비 커넥션 풀(`pg.Pool`) 크기 설정이 중요하나, 구체적 튜닝은 개발 일정상 별도 검증 단계로 남긴다.

## 9. 리스크 및 가정

### 9.1 리스크
- **동시접속 목표와 개발 일정의 충돌**: 1,000명 동시 접속을 안정적으로 처리하려면 커넥션 풀링, 인덱싱, 부하 테스트, 필요 시 캐싱·스케일링 전략 검토가 필요하다. 이는 2일·1인 개발 일정 내에서 충분히 설계·검증하기 어려운 항목으로, MVP 단계에서는 동시접속 목표를 실제로 검증하지 못한 채 출시될 위험이 있다.
- **Prisma 미사용에 따른 개발 속도 저하**: ORM 없이 `pg`로 직접 SQL을 작성하므로 스키마 변경이나 반복적인 CRUD 쿼리 작성에 시간이 더 소요될 수 있다.
- **1인 개발에 따른 병목**: 리뷰 없이 진행되는 단독 개발로, 설계 오류나 버그가 늦게 발견될 가능성이 있다.
- **예산 제약**: 저비용/무료 인프라를 우선하므로, 부하 테스트에 필요한 스테이징 환경이나 모니터링 도구 도입이 제한될 수 있다.

### 9.2 가정
- 사용자 인증은 이메일/비밀번호 기반으로 충분하며, 소셜 로그인은 필요하지 않다.
- 초기 출시 단계에서는 실제 1,000명 동시접속 트래픽이 발생하지 않으며, 이는 향후 목표로 설정된 수치이다.
- 배포 환경(호스팅, CI/CD)은 본 PRD의 범위 밖이며 별도 문서에서 다룬다.
